# 开发笔记

「神仙打架」的工程记录：怎么跑起来、怎么加一个角色，以及这个项目在**测试与实测**上反复栽过的那些坑——按帧数写死的常数、看着绿其实压根不会红的断言、量错了的指标。


## 本地开发

```bash
npm install && npm run dev  # 手机调试加 --host
npm test                    # 战斗内核测试
npm run build                # tsc 类型检查 + 生产构建到 dist/
npm run preview             # 本地起服务预览生产构建
```

`src/engine/`、`src/render/` 均不依赖 React；`engine` 还是确定性状态机（不用 `Math.random()`、
不读墙钟），同一份输入序列必须能回放出同一个结果，改动前留意别踩这条线。凡按时间推进的量
（衰减、绽放、逐字揭示……）都必须挂在 `GameCanvas` 固定 1/60s 步长的逻辑 tick 上推进，`draw()`
里只做插值——这个项目已经在"按渲染帧推进本该按逻辑帧走的量"上栽过三次（大招暗场衰减、血条
残影、火焰纹背光的绽放/自转），120Hz 设备上这类量会跑快一倍，新加计时器前留意别踩第四次。

### 别把帧数写进常数里

这个项目已经在同一类故障上栽过**四次**：一个按当时帧数算出来的常数，帧数改了之后静默失效，
没有任何报错，测试也照样绿。

| 常数 | 按什么定的 | 帧数改了之后 |
| --- | --- | --- |
| `KO_SETTLE_DELAY = 80` | 64 帧的老大招 | 大招拉到 600 帧，结算画面在屏幕还全黑时弹出 |
| 二郎神命中数测试的循环上限 `200` | 68 帧的老大招 | 循环在第 7 段就跑完，报「打空」而实际是没跑到 |
| 镜头回漂阈值 `100px` | 出招者只走 105px 的年代 | 位移变大后把「跟得很好但走得远」误判成回归 |
| 大招起手无敌 `60` | startup 还是 16 帧时 | startup 变 110，第 60 帧后无敌消失，大招被打断 |

**写常数之前先问：这个数是不是从别的数算出来的？** 是就别填字面量，从源头推导：

```ts
// 错：60 是当年 startup=16 时拍的
if (m.slot === 'sp100') f.invuln = 60;
// 对：从招式自身推导，帧数怎么改都成立
if (m.meterCost > 0) f.invuln = m.startup + SUPER_INVULN_TAIL;
```

测试里的循环上限、等待窗口、距离阈值同样适用——`for (let i = 0; i < 200; i++)` 这种上限
要按 `m.startup + m.active + m.recovery` 推导，否则测试会在帧数变化后悄悄失去意义。

**各系统实测出现率（次/回合，48 回合）**——这一行是给"建好了但玩家撞不见"那类 bug 用的常备体检：

```
run 17.98  chargeStart 7.75  lowAttack 4.75  roll 4.71  throw 3.38  backstep 2.50
jumpAttack 1.42  super 1.42（sp50 1.08 / sp100 0.33）  armorMove 1.40  tech 1.10
maxMode 0.69  guardCancel 0.58  blowbackCD 0.58  throwEscape 0.42  taunt 0.15
```

**量过之后确认不是问题的（别再查一遍）**：`chargeStart 7.75` 对 `maxMode 0.69`
看着像"AI 起手蓄气十次、九次没蓄成"，进而像是它在原地发呆——这个项目栽过"boss 突然发呆"
（出招键 64% 落空）那一次，所以这个比值很容易被当成同一件事。**实测不是**：
蓄气总共只占 20.9 帧/回合（双方合计，占对局帧的 0.6%），平均每次不到 3 帧，
每回合蓄到 6.25 点气，而且**蓄气过程中挨打 0.00 帧**。
那个比值的真相是：气够 50 时按下去当帧就转成 MAX，气不够时只是顺手蹭两帧，
两种都不是"站着不动"。这条留在这里是因为那个比值还会再被人看见一次。

**连段（n1→n2→n3 与取消）实测确实在跑**——这条曾经是死的，注释里还留着当时的说法
（"与连段同一个病：系统只存在于代码里"），所以隔一阵就会被重新怀疑一次。现在的数（次/回合）：

```
起手 n1 22.29 | n1→n2 4.25 | n2→n3 2.21 | n1→必杀 2.67(s1 .75/s2 .77/s3 1.15) | n1→大招 0.21
n1→n1 6.38（不是连段：前一下被挡/落空，链窗没开，重新起手）
```

也就是说**起手 22 次里约 4 次接得上第二段**，接上之后有一半能续到第三段。
比例不高不是机制坏了，是这个游戏的性质：一次交手大多数就换一两下（见上面的连段结构），
n1→n1 那 6.38 次正是"第一下没打实"的部分。别再把这个比例当成"AI 不会连段"。

**当前没有任何一个系统是死的**（这是量过之后的结论，不是假设）。
`systemsAlive.test.ts` 把它钉住了：它不守"多少算好玩"（那是调校，会随平衡漂移），
只守**不是零**——0.5 掉到 0.3 是调校，掉到 0 是这个系统死了。
挑衅最稀（48 回合 7 次），门槛按它定。第二条断言反过来查：
引擎 push 了而 SYSTEMS 表里没有的事件类型要报错——**新加的系统不进表，就等于没守**。

已经发生过至少四次的那类 bug：挑衅 0.00 次/回合、机动三件套 0%、
防御取消/MAX蓄气/吹飞攻击 0.00 次/局——每一次都是隔很久才偶然发现的。

**同一类 bug 现在有三条常备体检，各查一个方向**（它们都不守"多少算好玩"，只守"存不存在"）：

| 测试 | 从哪头查 | 抓的是 |
| --- | --- | --- |
| `systemsAlive.test.ts` | **结果**：跑 48 回合数每个系统出现几次 | 系统建好了，但对局里一次都不发生 |
| `aiActionsReachable.test.ts` | **源头**：AI_ACTIONS 每一项在权重表里有没有拿到过 >0 | 动作有名字有实现，但没有任何一张表给过它机会（机动三件套就是这么死的）；顺带查权重表里拼错的动作名——ai.ts 的 switch 没有 default，抽中不认识的动作会呆立一个决策窗 |
| `mirrorRun.test.ts` | **被所有人跳过的那一格**：自己打自己 | 模拟那一批测试全都以 `if (a === b) continue;` 开头（在抽对位，跳过是对的），合起来的后果是镜像战整套测试没跑过——而它是每趟阶梯的收尾（末关固定 FINAL_BOSS） |

三条合起来的道理：**一条断言故意跳过的那一格，正是需要另一条断言的地方**——
跳过这件事在别处是看不见的。

六关阶梯的两条测量口径（四关时代不需要，现在必须写清楚）：
- **每一级独立量，不用条件概率**。"打到了才算"会把后面几关的样本饿死——
  实测 72 趟下来关5 只剩 11 场（SE 11 点），关6 只剩 9 场。每级都从头给同样多的样本才比得了。
- **前五关的难度是一个分布，不是一个数**：对手是抽出来的，所以要跨种子跨角色平均。
  12 角色 × 10 种子 = 每级 120 场是这条曲线的最小可信样本。

两处已知的、量过但没治的：
- 跳入的胜率**曾经**不随关卡下坡（71/75/71/75）。现在是 58/77/77/68 —— 关1 最难跳、末两关次之，
  已经不是平线了（那不是某一次改动的功劳，是着地硬直、格挡可直接出招等累积的结果）。
  对空率仍然在 0.8 以上饱和，逐关分配与对空必殺技都复验过没用。
- ~~哪吒在第四关的通关率只有 5%~~ —— **已经自己好了**。气槽跨回合、爆气真的顶开、
  哪吒 n3 12→14 累积之后重量：哪吒 25%、孙悟空 25%、二郎神 35%、牛魔王镜像 45%。
  也验过关卡编排：四个人分别当最终关的通关率极差是 10 / 35 / 20 / **20** 点，
  牛魔王这个收尾是合适的，不需要改顺序。
- ~~**紧急回避在"已经在挡了"的时候按不出来**~~ —— **已解决**，做法与当初设想的不同，记在这里。
  病灶不在"哪个分支里少写了一条"，而在**回避没有自己的输入位**：引擎直接判 `block && move !== 0`。
  一个条件同时承担两件事，于是两头都错——条件每帧都成立（按住「防+后」这个最常见的防守握法
  会连滚不止，实测 120 帧滚 4 次、格挡 0 帧），而它只写在 idle/walk 里（人已经在挡着时按不出来，
  偏偏那正是最需要它的处境）。
  当初卡住的地方是"补进 block 分支就会连累 AI"——那也是同一个根因的另一张脸：AI 和玩家
  共用这条隐式契约，它每 26 帧换一次决策，在格挡里新按方向太容易了。
  **收成一位显式的 `InputFrame.roll` 之后两头一起解开**：输入层用「防御 + 新按下的方向」
  合成（边沿，所以按住不放只滚一次），AI 则按权重表里的 roll 项显式发这一位。
  代价是真的：AI 此前有一批**顺手滚**（付了 50 气做防御取消回避之后，手还按着，
  白得后续几次免费翻滚），拿掉之后每回合翻滚 关1 0.34→0.06、关4 1.05→0.81，
  整条阶梯与角色胜率都跟着挪了 ±5~8 点，于是补了两处调校：
  lv5 单独给一张更压迫的近身表（它是 react 最高的一档，丢掉的顺手回避也最多），
  白骨精血量 185→196（全名册最低血，而她换来的上下段优势在 AI 对局里本就量不出来）。
  阶梯 73/59/52/43/35/16（落差 14/7/9/8/19），角色胜率 40~62%，都比改动前更平。
- 60 秒读秒在 474 个回合里**一次都没响过**。看起来像"没用的 HUD"，但它不该改：
  平均 29 秒结束、一边倒只占 11%，说明节奏本来就落在时限之内；
  时限的作用是给"只跑不打"封顶（实测能拖到 89 秒），把它调短只会把正常对局也铡掉。
  这条记在这里是为了**别再重新发现一次**——0% 触发是设计结果，不是缺陷。
  但 0% 也意味着**这条路从来没人走过**，而它藏着三个错（都已修，见下一节）。

### 三档难度的六关曲线，以及末关那道坎到底有多陡

此前只有标准档的逐关数字。这次三档一起量（12 角色 × 15 种子 = 180 场/格，SE≈3.7，
玩家侧用 RUN_AI[2] 当"称职"的尺子）：

| 档 | 关1 | 关2 | 关3 | 关4 | 关5 | 关6 | 逐级落差 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 轻松 | 92 | 86 | 82 | 77 | 68 | 41 | 6 / 4 / 5 / 9 / **27** |
| 标准 | 67 | 67 | 53 | 44 | 33 | 13 | — / 14 / 9 / 11 / **20** |
| 修罗 | 37 | 34 | 29 | 26 | 22 | 4 | 3 / 5 / 3 / 4 / **18** |

**末关是一道坎，而且三档都是**：前面每级掉 3~11 点，最后一级掉 18~27 点。
原因在 react 的步长上——RUN_AI 逐关是 0.25 / 0.26 / 0.32 / 0.40 / 0.50 / **0.65**，
最后一步 +0.15 是全程最大的一步（前面依次是 +0.01 / +0.06 / +0.08 / +0.10）。
不是血量或伤害：`RUN_HP_SCALE` 与 `RUN_DMG_SCALE` 六关全是 1，没有任何数值加成在叠。

末关单独重量。这一格前后量了三次，**样本量每涨一档结论就翻一次**，如实全列：

| 末关 react | 样本/格 | 轻松 | 标准 | 修罗 |
| --- | --- | --- | --- | --- |
| 0.65（现值） | 480 | 42.9±2.3 | 13.5±1.6 | 5.0±1.0 |
| 0.58（候选） | 480 | 44.6±2.3 | 16.9±1.7 | 8.3±1.3 |
| 0.65（现值） | **1440** | — | **15.8±1.0** | **7.6±0.7** |
| 0.58（候选） | **1440** | — | **16.3±1.0** | **7.2±0.7** |

**结论：这个候选改动没有效果，不要再试了。**
480 那两行读出来像"修罗末关从 5% 抬到 8%、翻了 1.7 倍"，够诱人；
1440 重量之后是 7.6→7.2，差 0.4 点、约 0.4 SE，而且**方向还反了**；标准档 15.8→16.3 同理。
注意连**基线本身**都挪了（修罗 5.0→7.6，差约 2 SE）——也就是说 480 那一轮里，
被比较的两个数各自都不准，差值自然更不准。
这正是本文反复写的那条：**差值型指标的误差是复利的，要比单值指标多得多的样本**。

末关那道坎是真的（三档都掉 18~27 点，前面每级只掉 3~11），
但它**不是 react 那一步造成的**——0.65 与 0.58 打出来一样。真要治得另找旋钮。

**那个旋钮找到了：不是 AI 档，是"对面站着谁"。**
同一套末关 AI（RUN_AI[5]、标准档），只换 BOSS 是哪个角色，288 场/格（SE≈2.9）：

| 二郎神 | 哪吒 | 牛魔王 | 猪八戒 | 后羿 | 刑天 | 孙悟空 | 钟馗 | 铁扇公主 | 红孩儿 | 白骨精 | 雷震子 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 10 | 14 | **14** | 19 | 22 | 27 | 28 | 31 | 33 | 42 | 48 | 48 |

**极差 38 点**，而 react 那一步是 0 点。末关固定牛魔王（14%，全名册第三难），

**这张表的口径要看清楚：它给每个角色配的都是末关那套 AI（RUN_AI[5]）。**
所以它量的是"这个角色**当最终 BOSS** 有多难"，不是"他在第几关出现有多难"——
前五关用的是更弱的档（react 0.25~0.50，末关是 0.65），同一个角色在关 3 出现要好打得多。
换句话说 二郎神那个 10% **不会**真的发生在前五关，别拿它去论证"抽到他就完了"。
这条口径必须写在表旁边：不写的话，这张表下次会被当成"逐关难度表"用，而它不是。

也因此这 38 点的跨度**主要是角色特性，不是缺陷**——十二个人当对手时手感本来就该不一样，
把它抹平（比如按角色调 BOSS 血量）会让每一关打起来都一个样，
那是拿掉这个游戏最该有的东西去换一条更平的曲线。
中位数约 28——也就是说末关比"随便挑个人当 BOSS"难了约一倍，这才是那道坎的主要来源。

两条推论，都还没动：
- **末关想变好打，换人比调 AI 有效得多**。但最终 BOSS 本来就该难，
  牛魔王也不是最难的那个（二郎神 10%），所以这不是 bug，是**知道了代价之后的选择**。
- 更值得注意的是**前五关**：对手是随机抽的，而"当 BOSS 有多难"跨了 10~48%。
  同一档难度下，抽到二郎神开局和抽到雷震子开局不是一回事——
  **一趟阶梯的难度方差主要来自抽到谁，不来自关卡序号**。
  真要治，是让抽取按"当 BOSS 的难度"分层（前面的关抽软的、后面抽硬的），
  而不是继续拧 react；代价是会动到 `runDrawFairness` 守的那条均匀性。

  **量过之后决定不分层，理由如下。** 把 buildRun 的抽取跑 20000 遍，
  算每趟"前五关 BOSS 的平均难度"（用上表的值，越低越难）：
  均值 29.4，5% 分位 22.4、中位 29.4、95% 分位 36.4，极端 18.4~40.4。
  也就是说**五关一平均，单个 BOSS 那 38 点的跨度被压到了 90% 区间 14 点**。
  换算成重打次数（重打免费无限，所以这才是玩家真正感觉到的量）：
  22.4 那档约 22 次、36.4 那档约 14 次，**相差约 1.6 倍**——真实存在，但不极端。
  而分层的代价是直接对冲掉本文另一条明确守着的东西：
  「每个人在五个位置上都出现过」——软的角色永远排不到后面、硬的永远排不到前面，
  给他们做的招式、台词、主场背景就有一半玩家撞不见。
  1.6 倍的重打次数差，换不来"半个名册只在固定位置出现"。**保持均匀抽，待办划掉。**

另注意这份"当 BOSS 有多难"和角色矩阵（同档互打 36~60%）**不是一回事**：
后者量的是角色**当玩家**时的强弱，前者是**当对手**时的难缠程度，两者跨度差得远。

**一个被自己的小样本骗到的假设，记下来**：15 种子那轮读出标准档 关1/关2 = 67/67，
看着像"前两关难度完全一样"（react 只差 +0.01，解释还挺顺）。
加到 30 种子重量是 **66.7±2.5 / 59.7±2.6**——7 点的正常台阶，和早先留档的 69/60 对得上。
那个"defect"是抽样抖出来的。顺带把当时想好的修法也验了：lv2 的 react 0.26→0.30 之后是
66.7 / **53.3** / 54.4——关2 反而比关3 难，曲线直接倒过来。**假设和修法两头都是错的。**

### 打法偏置对「位置型」原型有效，对「信息型」原型无效

十二个角色交给同一档权重表时，AI 把他们打得**一模一样**：使用必杀的平均间距全落在
194~217px（十二个人只差 23px），而猪八戒——抓取距离 78、冷却 44、伤害 1.35 倍的投技型——
每千帧只投 1.0 次，比白骨精还少。十二种定位在数据里成立，一交给 CPU 就全变成同一个人。

`CharacterDef.aiBias` 按距离档给权重乘倍率（关卡仍管难度，角色只管"更爱做什么"）。
量完之后间距的极差从 23px 拉到 76px：刑天 146px（带霸体，敢在贴脸放慢招）、
白骨精 166、红孩儿 173……后羿的必杀使用率全场最高而投技全场最低，猪八戒正好相反。

**但白骨精那一版失败了，而且值得记**：给她近身必杀 ×2.4，总胜率从 44% 掉到 30%；
收到 ×1.5 仍是 31%。问题不在频率，在**这套 AI 没有读人这一层**——
她的价值是"两记必杀看起来一样，你得猜蹲还是站"，而 AI 的混合是随机权重、
不看对手在做什么，也不会因为对方猜错而追加惩罚。提高权重只是把 17~18 帧的收招反复送上去。
所以她是十二个人里唯一保持中立权重的：**位置型的原型（远射/投技/霸体/贴身）能靠权重表达，
信息型的原型不能**，后者要的是 AI 里还不存在的读人层。

### 上下段"读人层"做了又删：**猜得对不对不是杠杆，挡不挡才是**

上一节的结论（信息型原型表达不出来，因为 AI 不会读人）指向一件看起来显然该做的事：
给 AI 加一层读人——记住对手最近打上段还是下段，据此偏移防御姿势的先验。
做完了，量完了，**删了**。过程值得留着，免得下次再照着"显然"重做一遍。

做法：指数衰减地数对手的下段/中段起手，把蹲防概率从固定先验（落地 0.75 / 空中 0.25）
按观察偏移，封顶保证 AI 永远猜得错。

**第一版还引进了一个自己的 bug**：夹在 [0.30, 0.85] 是照着地面先验 0.75 拍的，
而空中先验 0.25 **比 0.30 的地板还低**——中立时就被夹上去，读到"对手全在打中段"
更是一分都降不下来。读人层在空中方向不但无效，还让 AI 比不读时更差。
两个先验共用一条绝对带就是这个下场；改成 [0.10, 0.90] 之后两个方向才各有 ±0.19 的活动量。

**修好之后再量，仍然是彻底的 no-op**（同一张权重表，react 0.31 / 0.33 跨过读人门槛，
十二角色 ×3 种子）：

| 打法 | 不读人 | 会读人 |
| --- | --- | --- |
| 只扫下段 | 挡下率 16%　胜率 28% | 挡下率 16%　胜率 31% |
| 只跳入 | 挡下率 34%　胜率 81% | 挡下率 34%　胜率 81% |

算一下就明白：地面先验 0.75 顶到 0.90 只多 0.15，而 AI 只在**它选择格挡的那些帧**里
用得上这个概率——一根筋的下段流打过来，只有 16% 被挡下。0.16 × 0.15 ≈ 2 个百分点，
埋在噪声里。**决定"套路好不好用"的是 AI 挡不挡（频率），不是它挡对没挡对（高度）。**

早期一次 stage2 vs stage4 的对比曾显示挡下率 10%→19%，看着像读人层生效——
那是**关卡权重表不同**（近身 block 2 → 3）带来的，不是读人。
跨档比较里混着两个变量，得用同一张表跨门槛做 A/B 才分得开。
留下的教训：**先算杠杆有多大，再决定值不值得做**——这次的杠杆算一步就知道只有 2 个点。

### 难度档：单动一个旋钮分不开档

标准档的末关 15%、六关连过 0.8%——那是给"练熟了再来"的人调的曲线，
第一次上手的人在中段就卡死。街机厅有投币续关，手机上没有，那就把选择交给玩家。

**只动 react 是不够的**：实测 react −0.12 也只把末关从 15% 抬到 19%——
对空饱和那堵墙（见下一节）压着，反应率再低也救不了末关。
三个旋钮一起动才分得开档，而血量与伤害恰好是玩家真正感觉得到的两项：

| 档 | react | 血 | 伤 | 逐关 | 六关连过 |
| --- | --- | --- | --- | --- | --- |
| 轻松 | −0.08 | 0.92 | 0.86 | 96/85/79/83/71/52 | 19.8% |
| 标准 | 0 | 1 | 1 | 75/63/60/48/40/15 | 0.8% |
| 修罗 | +0.10 | 1.05 | 1.08 | 52/23/27/27/13/2 | 0.0% |

第一版给的是 −0.12/0.85/0.8 与 +0.15/1.1/1.15，两头都过头了
（轻松的关1 到 98%，修罗的末关剩 2%）；收到现在这组才是"各让一步"而不是"换个游戏"。
**难度只挪 react，不动权重表**——难度改的是"看得多清"，不是"他爱做什么"，
后者是角色定位（aiBias），两件事不能混。

### 跳入为什么压不住：三个决策旋钮全是零，问题在几何不在行为

接着上一节「决定套路好不好用的是频率不是高度」往下追，量了三个旋钮，
**全都是零**（同一张权重表、十二角色 ×3 种子、单回合）：

| 旋钮 | 只跳入 | 只扫下段 |
| --- | --- | --- |
| 反应率 0.4 → 0.65 → 1.0 | 挡下 31/31/31%，胜率 86/86/86% | 挡下 19/26/33%，胜率 17/11/11% |
| 上下段读人（上一节） | 34% → 34% | 16% → 16% |
| 挡完就还手 | 31% → 31%，86% → 86% | 19% → 19%，17% → 17% |

跳入那一列三个旋钮一动不动——**反应率从 0.4 拉到 1.0（每一次都读到）都不改变任何东西**。
这已经是第五次撞上「对空饱和」那堵墙，但这次量到了墙后面是什么：

    AI 在对手空中时出招 628 次，打中 183 次（29%）；落地后又打中 72 次。
    同一段时间里跳入方打中 526 次。

也就是说 AI **不是不拦**（628 次尝试），是**拦不住**：跳入方的命中数是它的两倍。
成因是帧数几何——跳跃攻击的判定期有 14~15 帧，而地面普攻只有 3~4 帧，
一次下落覆盖的时间窗口本来就比对空的窗口宽四倍。这不是决策层能修的东西，
**再聪明的选择也改不了判定框在空中停多久**。

**但也别急着改帧数**：项目真正在守的门是「一次通关」而不是单回合胜率，
而那条门（`jumpInCheese`，守门线 45%）现在是 20% —— 单回合 86% 复利到整趟就剩这么多。
所以这一轮的结论是**不动**：诊断记下来，等哪天那条守门真的红了，
直接从帧数几何入手，别再去调决策层的旋钮了。

### 「AI 从来走不到」的分支，正是错得最久的那条

读秒判胜在 474 个 AI 回合里触发 **0 次**（平均 29 秒结束）。而玩家会龟、会跑，
走到那里比 AI 容易得多。去看了一眼，那条路上并排躺着三个错：

1. **发了 ko 事件**——那套演出是兵器脱手扎进地里、震屏 20、闪白、20 帧慢镜、镜头怼脸，
   而此刻"输家"正站着、血还剩一半。画面在演一件没发生的事。
2. **不置 victory**——胜利姿势与台词只在 `settleKo` 里点亮，靠时间赢下来的回合于是
   既没造型也没话，跟什么都没发生长得一样。屏幕上也没有任何字说明回合为什么结束了。
3. **判完不收手**——读秒**平局**时 winner 留 null、doubleKo 也是 false，
   `tick` 顶部那条「判完就不再收输入」的闸门三个条件一个都不成立，于是整场继续照打。
   实测：贴脸平局判定之后再打 120 帧，winner 从 null 变成 0、对手被打死——
   上层在结算延迟结束时才读 winner，读到的是被改写过的那个。**平局四秒后变成一方获胜。**

三个都不是手滑，是同一个成因：**这条分支的表演层从来没有被人看过一眼**。
单元测试查的是 `winner` 判得对不对（那一条一直是对的），没有人问过
「这一刻屏幕上在演什么、这一刻还该不该收输入」。

留下的方法：**先按"AI 从不进入"筛一遍分支，再逐条问它的表演层**。
这个项目里同类的还有——双 KO、大招演出中途被打断、竖屏遮罩期间。

### 用手写机器人比"打法强弱"是不成立的

平衡靠实测，而实测的常见做法是写一个只会做一件事的机器人（只按普攻、只扫下段、只跳入），
拿它的胜率当那种打法的强弱。**这条路对"有没有无脑解"有效，对"A 打法比 B 打法强"无效。**

同一个"只压下段"的策略，三次机器人构造给出的第一关胜率是 **96% / 63% / 14%**——
差别全在手调的节奏参数上（每 6 帧扫一次还是每 14 帧、接近时蹲不蹲着走），
和被研究的机制没有关系。基于这种对比去调数值，调的是机器人不是游戏。

还有一层：**同一个策略，"用得好不好"本身就是一个维度**。跳入的出手时机扫一遍就知道
（每格 24 场）——第 4/6/8 帧分别是 1%/2%/4% 的通关概率，第 12 帧是 **28%**。
小跳滞空 25 帧，出手越晚判定框越停在弧线最低点上，砸得更深、对手反应时间更短。
守门要按**玩家会找到的最好用法**量，不是按随手写的那一个：钉死一个时机的断言，
量的是"我碰巧写的那个用法"。同理下段套路的五种构造在第一关给出 56%~75%，
而那条断言当时的门槛正是 70%——换个构造它就翻面。

能用的判据是**绝对门槛**，不是横向对比：

- ✅ 「有没有哪个单一套路能打穿四关」——门槛清晰（一次通关概率），构造再怎么变，
  能通关的策略始终能通关（跳入那次就是四种构造下全线 88-100%）
- ✅ 「同一个机器人，改动前后的差」——构造固定，差值有意义
- ❌ 「下段比中段强还是弱」——换个节奏参数就能翻面

顺带一条：`vitest` 走 esbuild 剥类型、**不做类型检查**，临时测试里把 `InputFrame`
的字段名写错（例如并不存在的 `throwKey`）不会报错，只会静默失效 ——
量出来的 0% 是"这个机器人什么都没按"，不是"这个策略没用"。临时量具也要跑一次 `tsc`。

### 改动里多出来的 `rng()` 调用会把整条随机流洗牌

引擎是确定性的：同一份种子必然回放出同一场对局。好处是可断言，代价是**任何改变随机数
消费次数的改动，都会把它之后的所有决策整个重排**——量到的差里混着"洗牌"，和真实效果分不开。

大跳那次踩得很清楚：在逐帧的动作分支里加一句 `rng() < 0.45`，角色矩阵和阶梯形状同时乱掉
（哪吒总胜率窜到 67%、某把尺子量出 37 点的墙），而那多半不是大跳造成的。
改用一条**独立的随机流**（`mulberry32(seed ^ 0x9e3779b9)`）之后，主流不受影响，
量出来的才是这一改本身的效果——然后才看清它确实是负的。

新增随机决策时：要么单开一条流，要么接受"这次 A/B 量的是改动+洗牌的合成效果"并说明。

### 提交前跑 `npm run verify`，别把测试输出接进管道

`npm run verify` = `tsc --noEmit` + `vitest run` + 重跑字体子集 + `vite build`，一条命令一个退出码。

这条是踩出来的：曾经写成
```
npx vitest run 2>&1 | grep -E "Tests |FAIL" && npm run build && git commit ...
```
**管道的退出码是 `grep` 的，不是 `vitest` 的**——测试红了，`&&` 照样往下走，
于是一条红着的断言被提交了上去（下一条 commit 才修掉）。
**同一个坑有两种形式，都踩过：**
```
npm run verify | grep ...        && git commit   # 管道：退出码是 grep 的
npm run verify; echo "$?"        && git commit   # 分号 + echo：退出码是 echo 的
```
可靠的写法是把退出码存下来再判断：
```
npm run verify > /tmp/v.log 2>&1; RC=$?
[ $RC -eq 0 ] && git commit ... || tail -5 /tmp/v.log
```

**还原用备份，别用 `git checkout --`。** 做变异测试（改坏一处、看断言红不红、再还原）时
用了 `git checkout -- <file>` 还原，而那几个文件里还压着**没提交**的改动——
一条命令把它们连同变异一起冲掉了，而且不报任何错。发现时已经跑了两轮，
只能照记录重做一遍。改坏之前先 `cp` 一份，还原就 `cp` 回来，跟 git 的状态无关：
```
cp src/x.ts /tmp/x.bak && sed -i '...' src/x.ts   # 改坏
npx vitest run tests/y.test.ts                    # 看它红不红
cp /tmp/x.bak src/x.ts                            # 还原，不碰 git
```

### 多分辨率实测：窗口 resize 不生效时用 iframe 夹具

`resize_window` 在这套环境里报成功但视口不变（实测仍是 2560×1271）。
可靠的办法是拿一张一次性夹具页并排放几个 iframe——**App 在 iframe 里读到的
`innerWidth/Height` 就是 iframe 的尺寸**，于是 `vh/vw/clamp` 全部按目标分辨率求值，
一屏之内就能横向对比几档。

```html
<!-- 丢进 public/ 跑完即删，别让它进 PWA precache -->
<iframe src="/" width="667" height="375"></iframe>   <!-- iPhone SE 横屏，最窄 -->
<iframe src="/" width="844" height="390"></iframe>
```

顺带一条读图纪律：**要看某一档，就单独看那一格**。拿 2560px 的全窗口截图去判
667px 下的布局，会把居中的东西读成"偏左、右半边是死区"——我就是这么误判过一次，
`S.full` 本来就带 `placeItems: center`。

**补一条：夹具是给"改不动视口的那种浏览器"用的，不是所有工具都需要。**
上面那条坑是 `resize_window` 那一路的；换成无头浏览器（gstack 的 `browse viewport 667x375`）
视口是真的会变——进页面量一次 `innerWidth/innerHeight` 就知道该走哪条路。
能直接改视口时别搭夹具：一档一张原生分辨率的整图，字看得清；四格拼在 2560px 里再缩给眼睛看，
最窄那格会被压到读不出笔画，而"读不出"很容易被当成"没问题"。

**结算页怎么截**：它一趟要看六次，是常驻画面，但真打过去要几分钟。
`App.tsx` 里挂了一行 `import.meta.env.DEV` 下的 `window.__battle`（生产构建整句裁掉，
同 `renderer.ts` 里那层判定帧叠加），在浏览器里把回合按读秒判胜推过去就行：

```js
__battle.p2.hp = 1; __battle.timeLeft = 2;   // 等结算演出放完，再来一次，两回合即结算页
```

每回合都会重建 `battle`，所以第二回合要重新取一次 `window.__battle`。

**补拍脚本要核对内容，不只核对尺寸**：本轮补拍时漏写了 help / select 两支的导航，
截出来全是标题页，而"尺寸对不对"这条检查照样全绿——尺寸对不代表拍的是那一页。

### 屏幕上的空档要量画布像素，别从常数推

触屏控件躲画布里的 HUD 时，**别拿代码里的常数去推那条空档有多宽**。
`drawBars` 的外侧留白是按**当前名册里最长的那个名字**算的（四个字的「铁扇公主」把两侧
血条一起往中间推），所以空档随名册变；注释里写过"568 宽时约 188px"，实测左半边只有 **28px**。
按那个错数摆的「退出训练场」在 568/667 两档整个压在玩家血条上，缩字号治不了。

量法：血条是饱和的藤黄，扫 HUD 那一带的画布像素找最右一个 `r>180 && g>120 && b<120`
的点，就是左侧 HUD 的右沿（实测 568/667/844/932 四档分别是 250 / 294 / 306 / 337px）。

同一条经验的另一半：**两个固定定位的元素别去抢同一块空地**。退出键和挡位条各自
`position: fixed` 时，两边各写各的坐标，撞不撞全靠人算；把退出键并进挡位条那个盒子之后，
不重叠是排版给的，不需要再算一次。

**同一个数不要往注释里抄第二遍。** `TouchLayer.tsx` 顶上那段注释是**专门用来纠正一段
过时注释的**，而它自己也过时了：写着按键簇包围盒是 "right 20–252 / bottom 16–286
（格挡键伸到 252、吹飞键伸到 286）"，按 `BTN` 表算实际是 right 12–240（最外沿是**吹飞**）、
bottom 14–216（最高是**技能键**）——四个数、两个归属，全错。同一组错数还被抄进了测试文件的
头注。这类数要用就现算（`Math.max(...BTN.map(b => b.right + b.size))`），
注释里只写它是怎么来的，不写它等于几。

浮层要让开这簇键，也是同一条：那个让位宽度曾经是**两处各写一遍的字面量 250**
（提示条一份、陪练挡位条一份），都是照着「吹飞 176+64=240，加 10」心算的。
现在 `CLUSTER_INSET` 由 `BTN` 推出来，两个浮层 spread 同一份 `LEFT_OF_CLUSTER`。

### 七键并成五键：4.1px 的间隙，误触是必然的

七键那版量得出问题：最小间隙只有 4.1px（技三与大招之间），最小键径 54px。拇指接触面直径通常 45-57px，两颗键之间只隔 4px 时误触是必然的，而按错的代价恰好是最重的那一种——想放技三，按出大招，50-100 气当场蒸发。

三颗技能键因此合成一颗，按下的那一刻由摇杆方向决定放哪一招（键面实时写着会出的那一招）：方向 + 按键本来就是格斗游戏的语法，要记的从"三个位置"变成"一条规则"。现在最小间隙 **15.7px**、最小键径 60px。

这两个数由 `touchLayout.test.ts` 里「开发笔记报的最小间隙/键径与键表对得上」那条跟导出的 `BTN` 表对着（不是刮源码文本——正则漏掉一颗键会让整组断言一起变弱，而且不会报错），改了布局不改这里就会红——曾经过期过两次，而当时那句话点名的 `touchDoc` 测试**在仓库里根本不存在**，等于自称有人守、其实没有。

### 改了键面，教学文案不会跟着改——屏幕上一件东西只能有一个名字

右手那几颗键当初叫「拳 / 技1 / 技2 / 技3 / 大招 / 防」，是按引擎槽位命的名，
玩家没法知道按下去会发生什么，于是键面换成了招式名与「防御」（`touch-buttons.test.ts`
记着这次改动）。**换的只是键面**：提示条与轮播里仍写着「快按 拳 或 防」「贴身按拳 = 投技」，
而屏幕上从此没有一颗键叫「拳」。玩家要先把「拳」翻译成那颗最大的圆键，才用得上这句教学。
最露的一处是同一行里两个名字并存：「普攻命中后再按拳接段」。

这类漂移测试抓不到——两边都是字符串，各自都"对"，只有把六屏的文案抄下来并排看才显形。
现在全部收敛到界面自己的叫法（普攻 / 防御 / 技能 / 大招 / 吹飞），帮助页那套
「普攻键 / 技能键 / 大招键 / 防御键 / 吹飞键」本来就在用，只是没铺开。

同一次通读还捞出三条同类的：

- **渲染到屏幕的 800 个汉字里有两个不是简体**——日文的「対」（练対空）和繁体的「釁」（挑釁）。
  两个都是从注释里的行话抄进渲染文案的，所以注释里的 30 处也一并归了一，免得再抄一次。
  查法很省事：`extract-chars.mjs` 本来就为字体子集算「真正会渲染的字符集」，
  把它打出来扫一遍就行，不用逐个文件找
- **帮助页有五条只给了键盘字母**（受身 / 防御取消 / 投技解脱 / 爆气 / 吹飞），
  而这是个横屏手机游戏，键盘按 spec 只是调试用的副产品——拿着手机的人读到
  「倒地瞬间新按 J 或 L」，屏幕上没有 J 也没有 L
- **结算页那行分隔号自己撞了自己**：十二个关名里有五个自带间隔号（酆都·鬼门关…），
  外层再用「 · 」分隔，「第一关 · 酆都·鬼门关 · 钟馗」读起来是四段并列

### 单元测试看不见布局，隔一段时间要真的打开浏览器

418 条测试全绿的时候，截图一次抓到两个问题：
- 选人页的通关印放进名号下方那格空档，**挤掉了名号高度**——三个字的「二郎神」竖排排不下，
  被压成两列，画面上读作「神二／郎」。测试只查得到「有没有这个节点」。
- 标题页那行读作「**已通关** · 最快 4:37 · **已通关** 2/4 人」，同一个词出现两次。

改完界面就去看一眼，`npm run dev` 加一次截图的成本，比一条查不出布局的断言低得多。

**第三轮又是两个**（十二人名册 + 六关阶梯落地之后，466 条测试全绿）：
- 标题页写着「最远 第**undefined**关」——关序号的中文数字写死成「一二三四」，
  阶梯加到六关，第五关就取不到字了。
- 四个字的「铁扇公主」竖排折成两列，画面上读作「铁扇／公主」。
  **这是第二次栽在同一件事上**（上一次是通关印挤掉「二郎神」的高度 →「神二／郎」）。
  只把字号调小不够——差几个像素照样折；竖排要真的不折，得写 `whiteSpace: nowrap`。

也记一条这个环境的坑：**自动化标签页的截图会是旧帧**（rAF 被节流，DOM 更新了但没重绘）。
改完之后截图看起来没变，别急着推翻自己的修改——去量 DOM：
`getBoundingClientRect().width` 是 24 还是 48，一次就分得出一列还是两列。

第二轮又抓到一个，而这次跟布局无关：**陪练场的提示条在说谎**。
陪练场每帧把气灌回 100（`App` 的 `onTick`），于是两条跟气有关的提示同时失真——
开场那条说「上一回合攒下的 100 气带过来了」（陪练场哪来的上一回合），
之后「气槽已满」恒为真，而它的级别压过轮播，把提示条**永久钉死在同一句上**：
实测一分钟里只显示过 1 条提示。陪练场恰恰是玩家待得最久、最该轮播完十几个系统的地方。

教训不是"提示写错了"，而是：**测试都是拿正式对局的状态分布喂的**。
陪练场是一组正式对局里永不出现的状态（血常满、气常满、木桩不还手），
那片状态空间没有任何一条断言走过。只在一个界面里成立的前提，只有打开那个界面才看得见。

### 优化一个指标之前，先证明它量的是你以为的东西

「后羿是弓箭手，可打起来不像」——为这句话调过三轮参数，最后发现**错的是指标**。

用的代理指标是「200px 之外落地的伤害占比」，量出他 12%、全名册第 4，被只有一记
投射物的二郎神 14.4%、铁扇 12.4%、哪吒 11.3% 压过。看起来铁证如山。

它是错的：他三记必杀**每一记自身还带近身判定框**（伤害 16/15/18），起手动作在近距离
就打中了，于是大量"放箭"被记进了近身伤害。换成「必杀出手数 / 总出手数」重量：

```
后羿 48  铁扇 48 │ 刑天 38 │ 二郎 33  牛魔 33  哪吒 32  钟馗 32
悟空 30  白骨 30  雷震 30 │ 八戒 24  红孩儿 23        （每人 44 场）
```

**并列第一，中位数 32。** 他本来就是弓箭手，一个数都不用改。

在那之前基于错指标试过的三个旋钮，全都不起作用，且都有实测：
冷却砍 40% 出箭量只 +3%（一场 7200 帧、冷却 130 光 s1 就够放 55 次，他只放约 10 支
——冷却离瓶颈差五倍）；中距离压普攻权重出箭占比 49%→51%，胜率却顶破 65% 上限；
"让他站到远处"更是无从谈起——远档（>350px）他只占 6% 的帧，而二郎神 5%、哪吒 4%，
**全名册都一样**，那组权重几乎从不生效。

**横向对比只花了一次测量，把前面三轮全部推翻。** 单角色的绝对数字读不出对错，
同一把尺子量过全体才知道 48 是高还是低。

### 别拿一个恰好会成功的信号当验证

`npm run verify | grep -E "Tests|error" && git commit` ——**grep 匹配到错误行也算成功**，
于是两个 `error TS` 一路提交了进去。判成败要显式取返回码：`npm run verify > /tmp/v.txt; echo "RC=$?"`。

同一个毛病在这个项目上付过两次代价。另一次更贵：想把「跳过的条目不必退避」做成条件执行，
实际把 `time.sleep(90)` 整条删掉了——`if r == 'skip': continue` 恰好是循环体最后一句，
等于什么都没做。而 `ast.parse` 通过、脚本打印 `ok`，看起来一切正常。
更糟的是 sleep 那行后面挂着两条注释（「skill 红线：别猛捶单账号、检测到限流要退避」），
它们被甩到了 `continue` 下面——**注释还在，退避没了**，下一个人 grep 到那句红线
只会更确信节流仍在生效。本该防止回归的注释，成了掩盖它的东西。

改完脚本要**把改动处读回来逐行核对**，或者用 AST 断言结构（"退避必须是循环体最后一句"），
不能靠"语法通过 + 打印成功"。

### 红检失灵的六种形态

改完代码要**故意把它改坏，确认测试会报**——否则你不知道那条断言到底守没守住东西。
但红检本身也会失灵，而且失灵时看起来和"代码是对的"一模一样。这六种在本项目上都真实付过代价：

| 形态 | 症状 | 实例 |
| --- | --- | --- |
| **① 打在弱用法上** | 摘掉机制，测试照样绿 | 对空的挡下率用**第 6 帧**出手的跳入去量——那是最弱的时机，AI 反应再晚也挡得住。换成第 12 帧（最强时机）才量到 57%→9% |
| **② 阈值不实测** | 破坏了也在阈值内 | 道具反应的干净挨打率凭感觉写 0.6，而**故障状态才 0.35**；气槽占比写 0.30，而大招伤害翻三倍也只到 26%。两条都是"永远绿的断言" |
| **③ 破坏没摘干净** | 只摘了一半，另一半仍在起作用 | 跳入木桩的位移只摘掉**地面分支**，空中那半仍在推进，距离照样缩了一百多；摘掉对空的"响应分支"却留着"読み的 key"，代码落到通用的读招分支上照样防 |
| **④ 打在机制的近邻上** | 断言测的是周边现象，不是机制本身 | 版边压制的三条测试（走出去比例、版边时长、胜负相关性）**把 PIN_FLEE 设成 1 全部照过**。改成直接量 `pinning()` 砍没砍逃跑权重、以及"对手贴墙时 AI 的后退帧占比"（3.0% vs 4.0%）才抓得住 |
| **⑤ 破坏根本没生效** | 脚本报错／改到别处，测试"绿"得跟没破坏一样 | 用 python 打补丁时字符串里嵌了中文引号，脚本抛 SyntaxError、文件一个字没动，红检当场"通过"。**破坏没生效的绿，和真正的绿长得一模一样**——所以红检要确认改动**确实落地**（看脚本退出码、或回读那一行），别只看测试结果 |
| **⑥ 红着，但报到了别的断言上** | 确实红了，可报出来的名字跟病灶对不上，顺着它查会先绕一圈 | 把横幅第四行的 y 从 232 挪到 300 做红检，本该报"压到人物头顶"，实际先报的是隔壁那条**「开场白那行根本没描边」**——因为那条测描边透明度的断言用 `startsWith('strokeText@232')` 写死了 y，一挪就什么都筛不到。断言里写死具体值不只是脆，**坏的时候还会指错方向** |

合起来是一条：**挑最能暴露机制的用法、用实测定阈值、把破坏摘干净、确认断言打在机制本身、
确认破坏确实落地、并且看清楚红的是不是你要的那一条。**

第六种还有个更一般的说法：**断言里凡是写死的具体值（坐标、字段路径、整条表达式），
都是一次待爆的哑弹**。本会话炸了四次：App 那条接线断言连炸三次（先钉字段路径
`battle.p2.def.quotes.intro`、再钉整条三元表达式，两次都是我**自己的下一次改动**打掉的），
第四次是同一次改动打掉了**隔壁**那条。治法是钉**关系**不钉值——
取出那个 prop 查它由哪几件事组成、把 y 导出成常量让两边共用、按渲染层常量算出头顶位置。

另有一条不属于红检、但同样是"看起来已经核对过了"的坑：**测试总数对不上时，
源码里的 `test(` 计数不是证据**。`test.each([...])` 一行会展开成 N 条，
按源码数永远数不出来。本会话就靠它差点判错：同名覆盖掉一个已有测试文件之后，
两个提交的 `^test(` 数完全相同（各 3 条），而实际跑起来是 7 条变 3 条、净丢 4 条。
最后是**逐文件跑 vitest 再 diff** 才定位到。数量对不上就按运行结果比，别按源码比。
还有一个附带规矩，它被破坏过五次，所以措辞换了两版：

**红检还原之后，回读那一行、确认它真的没了——别信还原命令的沉默。**

### 上一节是"破坏没打中"，这一节是"断言压根不会红"

红检失灵至少还需要你去破坏一次才暴露。下面这五种更隐蔽：**它们在任何代码下都是绿的**，
连破坏都不用做。全部来自同一轮改动——我给两个浮层加了"让开右下角按键簇"的守门，
守门自己一条都不结实，是一轮代码审查逐条挑出来的。

| 写法 | 为什么永远绿 | 治法 |
| --- | --- | --- |
| **① 恒真的比较** | `expect(CLUSTER_INSET).toBeGreaterThanOrEqual(clusterLeft)`，而 `CLUSTER_INSET` 就是 `clusterLeft + 10`——`x+10 >= x` 对任何键表都成立。更糟：解析键表的正则崩了、`clusterLeft` 变成 `-Infinity`，它照样绿 | 钉**精确关系**：`toBe(clusterLeft + 10)` |
| **② 拿插值跟它自己的来源比** | `expect(LEFT_OF_CLUSTER.right).toContain(\`${CLUSTER_INSET}px\`)`，而那个字符串就是用 `CLUSTER_INSET` 拼出来的 | 删掉。它测的是模板字符串会不会插值 |
| **③ 空过（vacuous pass）** | 把 `pane` 提到模块级省得查四遍，之后「返回不在滚动区里」写成 `find(pane, isBack).length === 0`——说明区一旦没了，`pane` 是 `undefined`，`find` 返回 `[]`，**在根本没有滚动区的时候这条也绿** | 取不到就地 `throw`，让后面几条带着话失败 |
| **④ 两份规则只守了一份** | 同一个让位宽度写在两个文件里，而断言只 grep 了其中一个源码；另一个文件的注释还写着"某某断言守着这个数"——**那句话是假的** | 守共享的那一份；两份都要查时就循环查两份 |
| **⑤ 跨文件耦合没人守** | 类名挂在 `.tsx` 里、渐变写在 `index.html` 的内联样式里。谁清理 CSS 时删掉那条规则，tsc 过、测试过、`check-anchors` 也看不见（它当时只扫 `.ts/.mjs`，带 JSX 的测试整个不在体检范围内） | 把两头都写进断言；顺手让体检脚本也扫 `.tsx` |

还有一条关于**反面断言**的：我一度写成"禁止出现手写的 `right: calc(Npx + env(...))`"。
它两头都不成立——**既会误伤**（任何一个同样贴右边缘的无关元素都长这个样，
静音键正是，只因为写成模板字面量才侥幸躲过），**又能被绕开**（换双引号、换反引号、
`+` 前少一个空格、干脆写 `right: 250`，四种都过）。
**能写正面断言就别写反面的**：与其禁止某种拼写，不如要求"必须用共享的那一份"
（`expect(src.includes('...LEFT_OF_CLUSTER')).toBe(true)`）——正面断言不会误伤，也没法靠换写法绕。

同一类还有"只认一种拼写"：底色那条只查 `background`，而把它改成完全等价的
`backgroundColor` 会以「说明区没有底色」这条**假消息**报红。断言要验的是行为（有没有暗底），
不是属性名怎么拼。

验收办法就一条：**每条守门都真的改坏一次，看它红**。这一轮五条守门逐条做了变异测试
（删掉 `.sx-more` 规则 / 去掉 spread / 解冻共享样式 / 摘掉出口 / 键表变大同时写死让位宽度），
五条全红才算数。其中"把推导换成今天正好正确的字面量 250"是**绿**的，那是对的——
今天 250 就是对的，键表一动它才该红，而那一步验过确实红。

原来的写法是"还原不要用 `git checkout`"，理由是它会**退掉未提交的改动**（四次：
四套胜利姿势、角色数值、TouchLayer 的四处修改，以及写完还没提交的 niumo 那组 vsIntro，
最后一次是规矩已经写在这里之后又犯的）。第五次换了个花样：对着**untracked 的新测试文件**
跑 `git checkout --`，它对未跟踪文件**根本不生效**，那行破坏代码就留在文件里，
而测试当时还是绿的——靠 `grep -c` 复查才发现。
也就是说光记住"别用某个命令"不够：**这个坑的本质是把"命令没报错"当成了"状态已还原"**。
用改动前的文件副本还原，然后 `grep` 一次。

### 一条守门被两个机制同时满足，就不再守任何一个

跳入那条断言（"单靠跳入打不穿阶梯"）原本是对空的回归网。后来补了着地硬直，
而着地硬直**独立地**压住了这个循环——于是把对空整个摘掉，那条断言照样绿。
它守的性质还在，但它已经不是任何一个机制的回归网了。

红检时要问的不是"测试红了吗"，而是"**它是因为我摘掉的那个东西红的吗**"。
这一条上连着栽了两次：摘掉"对空响应分支"没红（reading 仍为真，代码落到通用的
"读到出招就防"那一支，跳跃攻击期间 `foe.move` 是有值的）；换成第 6 帧出手量也没红
（弱时机，AI 反应再晚也挡得住）。打在第 12 帧、并且摘掉**読み的 key 里那个滞空判断**
才量到真相：挡下率 57% → 9%，通关概率 28% → 73%。

守机制的测试要打在**最能暴露那个机制的用法**上。

### 判定框比兵器画得远——"还没碰到就被打了"（**已量，未修**）

玩家反馈：「经常武器/招数还没接触对方，就显示被打了」。量了每一招在判定帧里
**刃尖能伸到的最远处**对比**判定框前沿**（都相对脚底中心，已排除投射物招式，
投射物的判定属于飞出去那颗、不属于兵器）：

```
普通技(n2/n3)  牛魔王 n3 判定125/兵器78(+47)   二郎神 n3 123/82(+41)
               铁扇公主 n3 116/71(+45)          猪八戒 n3 +59
必杀技(s1~s3)  二郎神 s2 判定280/兵器135(+145)  牛魔王 s1 225/128(+97)
超必杀(sp)     牛魔王 sp100 判定360/兵器120(+240)  二郎神 sp100 360/171(+189)
               铁扇公主 sp100 380/206(+174)
```

n1 全员都在 12px 内（没问题），**n3 是日常最扎眼的一档**：多出来的 40~60px
接近一个身位宽，玩家一眼就看得出"打空了却算中"。

**修法要分两类，别一刀切：**
- **普通技**：判定框是调过平衡的、有一堆守门钉着，动它风险大；
  而 `weaponScale` 这个字段本来就是干这个的（"招式名承诺变长的招"）。
  实测把 n2/n3 的倍率提到 1.1~2.0 就能让刃尖够到判定前沿，**零平衡影响**。
- **必杀/超必杀**：同样算法要 2~6 倍才够（牛魔王 sp100 要 6.0×，78px 的混铁棍会变成 468px、
  半个场子长），显然不能这么修。这一档的射程是**特效**（曼陀罗背光、光束、冲击波）撑起来的，
  要么认下这个约定（特效到了就算到），要么缩判定框——那是平衡改动，得单独量。

### "新角色看着都一样"的根是美术素材，不是配色（**已补齐**）

曾经 `public/chars/` 下只有 `erlang / nezha / niumo / wukong` 四个目录，另外八个整条走
程序化兜底（圆头 + 胶囊四肢），画面上因此是**两类东西**：四个是画出来的、八个是火柴人。
玩家那句「新增神话人物的头像不该用默认」说的就是这个，而且比"配色一样"严重得多。

**现在十二个人全有**：`public/chars/<id>/` 下 23 张部件图（十二个 `torso.png` + 十一个
`head.png`——刑天 `headless`，那对眼睛和那张嘴画在躯干上，不是缺件）。
规格、提示词模板、生成脚本与踩过的坑都在 [`docs/art-missing-parts.md`](docs/art-missing-parts.md)，
管线本身见 [`docs/art-pipeline.md`](docs/art-pipeline.md)。

这一路留下两条还用得上的经验：

- **补头/躯干不需要改代码。** `parts.ts` 是逐件挂载的：哪个字段有图就用哪张，缺的各自独立回退。
  但探测列表只有 `head`/`torso` 两件（管线只出这两件，探七件等于每个角色白付 5 个 404）——

  牛魔王不会长出两对角

### 已经试过并退回的方向

**气绝／眩晕（KOF97 的スタン）——量过之后决定不做，理由是这个游戏的连段结构撑不住它。**
这是拳皇 97 里唯一一个本作完全没有的大系统，所以每隔一阵就会被重新想起来。先量了连段：
48 回合、513 段"不间断受控"，每回合 10.7 段，**中位数 1 下**，75% 分位 2 下、95% 分位 4 下，
最长 14 下；≥2 下的只占 31%，≥4 下的占 5%。
也就是说**这是一个对拼／试探型的游戏，不是连段型的**——一次交手绝大多数就换一两下。
而气绝槽是给连段型游戏的奖励：靠短时间内密集挨打把槽填满。
在这个结构上给它定阈值，两头都是坏的：
按 4 下能填满去定，它会常态触发（每回合就有 0.5 次机会），对局变成一串硬直；
按 8 下去定，它一局都不会响一次——就成了本文反复记的那种"建好了但玩家撞不见"的死系统。
真要做，得先把游戏改成连段型（更长的 hitstun、更宽的取消窗口），那是另一个游戏。

**`vsTaunt`（按对手分的挑衅台词）——已做，做法与另外三张表不同，别照抄。**
胜/负/开场那三句是"取一个字符串直接显示"；挑衅那句是**招式的 name**
（`tauntMove` 把它塞进 Move.name，借 s1 的坑位在头顶浮字），而那个 Move
**按角色缓存在 `f.def._taunt` 上**。所以缓存的是招式的**形状**，
`name` 每次调用都用 `tauntQuote(f.def, foe.def.id)` 覆盖一遍——
把 name 一起缓存进去的话，它会锁死在第一个挑衅过的对手身上，换关卡也不变，且不报错。
`vsTaunt.test.ts` 专门守这条：同一个角色先后对两个对手挑衅，浮字必须跟着换（回落那一支也要）。
另：`engine/battle.ts` 因此 import 了 `data/quotes`——这是 engine 唯一一处反向依赖 data，
不成环（`data/quotes` 只依赖 `engine/types` 这个叶子），选它是因为把回落再抄一份
才是这个项目栽过五次的那种漂移。挑衅浮在头顶，上限 10 字，四个坑位里最紧的一个。

## 添加一个角色

- `src/data/characters/` 下新建一个文件，参照 `nezha.ts` 写满 8 招：`n1~n3` 普攻连击、
  `s1~s3` 带冷却技能、`sp50`/`sp100` 两档大招
- 在 `src/data/characters/index.ts` 里 import 并加进 `CHARACTERS` 数组——这一步就是把新角色
  纳入 `validateCharacter` 检查的地方，`tests/characters.test.ts` 的全角色测试跑的正是这个数组
- 每个招式的 `motionId` 必须是 `src/data/motions.ts` 里已有的键，不存在会被校验器挡下
- **四句台词各写一句**，缺一句或写长了都被校验器挡下。四句坑位不同、上限也不同：
  `quotes.intro` 开场（关卡横幅第四行，≤14 字，由**对手**对着玩家说）、
  `quotes.win` 胜（胜利姿势，≤18）、`quotes.lose` 负（结算页，≤18）、
  `quotes.taunt` 挑衅（头顶浮字，最窄，≤10）。
  写完顺手跑一遍 `node scripts/subset-font.mjs`——新字不进字体子集的话，
  它们在 Android 上会**静默**回退成黑体（`font-coverage` 那条会报，但它排在 vitest 里，
  而子集脚本排在 vitest 之后，所以先跑脚本再 verify）
- 三张**按对手分**的关系表是可选的，写不出就不写，回落到上面那四句：
  `vsIntro`（开场）/ `vs`（胜）/ `vsLose`（负）。取法一律走 `data/quotes.ts` 的
  `introQuote`/`winQuote`/`loseQuote`，别在用的地方内联 `?? 回落`——这条规则漂移过五次。
  键写错一个字母不会报错也不会崩，只是那一句**永远不出现**（校验器现在会挡下不存在的 id）
- **头饰 `crown` 必填**（无头角色除外）：大招特写、对局里那颗头、选人页立绘共用同一件，
  是玩家认出"这是谁"的凭据。十二个人不许有两个戴同一件（`crown.test.ts` 守着），
  所以加第十三个人时得挑一件没人用过的；颜色同样 6 位 `#RRGGBB`。
  刑天那种 `headless` 的**不要给**——渲染层压根不画那颗头，校验器会拦。
  另外：`public/chars/<id>/head.png` 存在时走美术素材那一支，头饰不画（不会叠成两层）
- **兵器 `weapon` 必填**：形制（`kind`）决定画法，`drawWeapon` 里一种一支；
  九种里挑一种，真同类才允许共用（哪吒与红孩儿同为枪、牛魔王与雷震子同为棍），
  共用时长度/握点必须分得开，否则画面上是同一件东西（`weapons.test.ts` 守着）。
  要一件新形制就得同时在 `drawWeapon` 里补一支——那里最后一支是 else，漏了不报错、只会画成棍子
- **格斗定位 `role` 必填**（四到六个字）：选人页上玩家判断"这个人怎么打"的唯一入口；
  也是数据自己的约束——写不出一个不重复的定位，说明这个角色没有存在的理由
- `palette.main`/`palette.accent` 必须是 6 位 `#RRGGBB`，3 位简写或颜色名同样会被校验器挡下
- 跑一遍 `npm test`，帧数/伤害非法、fx 帧越界、招式 id 重复等问题会连同新角色一起报出来

## 架构一览

纯前端零后端，Canvas 2D 手写引擎：固定 1/60s 步长、AABB 碰撞判定、参数化骨骼动画、
粒子特效、Web Audio 实时合成音效，全程不依赖任何图片/音频素材即可运行；
`/chars/<id>/` 下放 `head.png` 与 `torso.png` 就会自动换装，而且是**逐件**的——
有哪件用哪件，缺的那件单独回退到骨骼画法（刑天就只有 torso，没有头，照样挂得上）。

标题页会记一行闯关记录（最远第几关 / 最快通关用时，存在 localStorage）——通关一次和
从没打过是一样的话，这一趟就没留下任何东西。不做分数：这个游戏没有得分体系，
硬编一个只会是个假指标。

支持 PWA 离线安装，横屏专属。

## 字体

竖排招式名、朱砂印、关卡横幅、角色名这套"古籍宋体"排印，用的是自带的 `ShenxianSerif`——
Noto Serif SC 的字符子集（`public/fonts/ShenxianSerif.woff2`），只收本项目真正会渲染到屏幕上
的字符，不是完整字体。系统字体栈（`Songti SC`/`SimSun`/`Noto Serif CJK SC`）留作它没加载出来
时的兜底，但那三个字体名在 Android 上都没有对应字体，不自带子集的话中文会静默退化成黑体。

新增角色、招式名、关卡名或界面文案后，重新生成子集：

```bash
node scripts/subset-font.mjs   # 需要 fonttools（pyftsubset），构建期工具，不是运行时依赖
```

## 音乐与音效

战斗背景乐同样是程序化合成，不依赖任何音频文件：一条低音、一记堂鼓、一句稀疏的五声旋律
（宫商角徵羽），逐关升调提速（92→116 BPM，主音各不相同）。旋律是写死的四小节乐句而不是
随机生成——随机听两遍就露馅，而且"同一关每次听到同一句"本身就是可回放性的一部分。
音量压在音效之下，静音键一并管它。

排程用 `AudioContext.currentTime` 而不是逻辑帧。这不违反本项目"按逻辑帧推进"的规矩：
那条规矩管的是**游戏状态**（衰减、绽放、读秒），音频调度本来就属于墙钟域，挂逻辑帧
反而会在掉帧时把节拍拖走。

音效的分派集中在一处纯函数（`sfxForEvent`）：散在各分支里的话，新增事件很容易忘了配音，
而「哪种声音从来不响」这种事肉眼看不出来——实测就抓到过一次：挥空声只在普攻起手时响，
一记打空的必杀完全无声，而空挥率有 46%。

绝大部分音效是 Web Audio 实时合成（方波/噪声 + 短包络），不依赖任何音频文件。仅大招重击
命中与 KO 这两个时刻换成了真实采样，取自 [Kenney](https://kenney.nl) 的 `Impact Sounds`
素材包（CC0，公有领域），来源与 sha256 见 `public/sfx/SOURCE.md`；采样加载失败或离线时会
自动回退回合成音，不会静音。

## 部署

gh-pages 分支只当静态产物的存放处，对外由 EdgeOne Pages 拉这个分支发布（见
`.github/workflows/deploy.yml`）。

### `edgeone.json` 里除 `/*` 以外的规则一条都没生效（**已量，未修**）

线上实测：`/assets/*`、`/fonts/*`、`/chars/*`、`/sfx/*`、`/skel/*` 拿到的全是兜底那条
`/*` 的 `no-cache, must-revalidate`。也就是说 449KB 的 bundle 加 344KB 字体每次进站都在
回源验证，本该缓一年。

```bash
curl -sSI https://fight.newzone.top/assets/index-<hash>.js | grep -i cache-control
# 期望 public, max-age=31536000, immutable；实际 no-cache, must-revalidate
```

**排除掉的两条**（别再走一遍）：

- **不是数组顺序。** 试过把 `/*` 挪到最前面当垫底值，部署后（`curl /edgeone.json` 确认
  线上确实是新顺序）响应头一个字没变。`/*` 在头在尾都赢。
- **不是 `/chars/*/*` 那条非法规则拖累的。** 官方文档写明 source 中最多一个 `*`，
  `/chars/*/*` 两个，是该删；但 025-kuafu 的 `edgeone.json` 里没有任何多通配符规则，
  它的 `/assets/*` 同样不生效——两个项目一样的症状。

还没试的：给 `/assets/*` 加一个 `/*` 没有的 header 键（例如 `X-Test-Rule`）发一次，
看它出不出现。出现就说明具体规则是命中的、只是 `Cache-Control` 被 `/*` 覆盖；不出现
就说明具体规则压根没匹配上，得去查 source 的写法（文档说 `*` 是 URL 路径通配符不是
文件系统 glob，可能不跨 `/`）。

这条坏得没有任何症状——站点功能全对、控制台干净，只有看响应头才发现。
